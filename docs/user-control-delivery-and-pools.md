# 用户管控：缓存发送、等待与连续随机策略

本功能沿用用户管控权限：默认仅超级管理员可见、可写；委派仍使用原有策略读写、名单、覆盖和审计权限。所有新动作默认关闭，不改变未配置用户的请求。

## 可视化入口

- 安全与限制 → 用户管控 → 策略 → 模型和渠道规则 → 请求与响应动作：开启随机上游等待、缓存后逐字限速发送。模型与渠道筛选可单独或同时使用。
- 策略 → 时段：开启“随机连续生效”，分别填写连续生效、休息的最短与最长分钟数。时段内仍可使用全部已有限额和动作。
- 用户管控 → 策略池：新建命名池，勾选已有完整策略，填写策略保持时长。池可像普通策略一样被多个名单、订阅和用户覆盖复用，不是单条策略内的专项规则分组。
- 用户管控 → 审计：记录命中的池、成员策略、时间段、动作、上游处理阶段耗时和输出速率、实际发送耗时和输出速率、发送是否完整。

表单复用项目 Dialog、Field、Input、Switch、Checkbox、现有策略编辑器；`TransportRange` 是本功能的范围字段组合，不另建弹窗、列表选择器或编辑器框架。七种界面语言均提供翻译。模型编号、策略编号、JSON 字段和协议枚举仍保留技术标识。

## 发送契约及计费

- 仅支持 HTTP Chat Completions、Responses、Claude 的单路文本 SSE 请求（`stream=true`）。音频、多路候选、非流式、任务插件、WebSocket 不支持；命中不支持的请求会明确拒绝，不静默绕过限速。
- 请求转交上游前，从最短与最长等待毫秒数内随机选一次；整个请求重试不重抽、不重复等待。允许非负整数，取消原 120000 毫秒业务上限；0 表示不等待。超长毫秒等待分段计时，避免时间单位转换溢出。
- 完整缓存上游返回后，按 Unicode 字符逐个发出文本增量。每字符随机选择配置范围内的速率，允许非负整数（最小 0），不设每秒 1000 字符业务上限。随机抽中 0 时，该字符不额外等待；不会除零，也不会永久暂停。最小与最大均为 0 时仍先完整缓存，再不额外等待地发送。速率不是模型分词器的 token 数。保持结束事件、工具调用、签名、加密 reasoning 内容和真实 usage 的协议语义；Responses 序号重新连续编号，工具调用只发送一次。无法安全重放的流在发出任何缓存正文前拒绝。
- 两项范围均须最大值不小于最小值。无业务上限不代表无限数值精度：网页填写值须为 JavaScript 安全整数，接口仍受服务端整数表示范围约束；超精度／溢出值拒绝，不静默截断。极高发送速率受计时器和实际网络性能限制，不保证实际达到配置值。原有超时、缓存与并发保护不变。
- 成功状态却返回非 SSE JSON、流缺少完整结束标记、无效 JSON、多候选等，均不直接整包返回来绕过配置。上游真实 HTTP 错误仍返回真实错误状态。
- 每实例同时最多 32 个缓存／发送请求；每请求缓存上限 16 MiB、单个 SSE 事件上限 1 MiB，缓存和重放共用 30 分钟上下文期限（前置等待另计）。外部代理、上游或客户端可能提前超时；实际网络写入还受服务器写超时控制。超限或存储故障取消上游并返回错误。
- 缓存放在操作系统临时目录，创建模式 0600（Windows 实际访问控制还由临时目录 ACL 决定）；退出路径关闭并删除文件。进程崩溃可能遗留临时文件，运维需按本服务专用前缀清理，不应扫描或删除其他应用文件。
- **先完整缓存必然增加首包延迟、磁盘读写、解析和 JSON/SSE 封装开销，并延长连接和并发槽占用时间**。即使缓存主体落盘，重放时也需要有界的内存解析缓冲；不要当作零成本功能。建议先对少量用户开启，检查代理与客户端超时。
- 从上游等待开始直至发送结束，为原有全局／专项并发桶续租，防止长等待或慢放超过原有 10 分钟 TTL 后提前释放名额；多实例仍建议使用 Redis。
- **真实用量和结算不变**：上游产生消耗后按原计费逻辑结算；不是等用户看完才扣费。只延迟消费日志的写入，完整发送结束后再显示正常完成记录。客户端断开、发送超时或异常时，仍保存已发生的真实消费，并标记发送未完成，不能抹掉账单或伪造成功。
- 用户日志的耗时、首包和速率采用实际下发阶段数据；`client_output_tps` 为真实完成 token 数／实际下发秒数，不以字符数冒充 token 数。发送失败时速率为不可用，不回退到更快的上游速率。管理员元数据保留原上游日志耗时、首包，以及网关实测的上游处理阶段数据；后者包括正常验证、转发和结算阶段开销，不冒充供应商单独报告的纯生成时间。
- HTTP 流已开始后发生的断开，HTTP 状态无法追溯修改；消费日志的流错误状态和管控审计成功标记会反映未完成，不以 HTTP 200 推断成功。模拟响应仍明确标记且不收费，和实际输出限速是不同功能。

动作示例（置于原有专项规则的 `actions`，可放在时段限制内）：

```json
{
  "delay": { "min_ms": 1000, "max_ms": 3000 },
  "delivery": { "min_cps": 10, "max_cps": 30 }
}
```

## 连续随机生效与策略池

已结算的真实用量会在慢速发送前先写入仅管理员可见的“上游已结算，发送待完成”审计，包含真实额度、输入／输出令牌和请求标识；它不代表客户端请求完成。完成消费日志仍延迟写入；进程崩溃时可按请求标识人工对账，但不会自动恢复或补齐用户消费日志。日志数据库写入故障沿用现有错误上报，不构成事务性发件箱或跨库原子保证。

- 随机时段采用“休息 → 生效 → 休息”的连续区间，不是每个请求独立抛硬币。开关关闭时恢复整个匹配时段持续生效。时段之外与休息期间，策略基础限制和其他来源的限制仍然有效；没有命中窗口时仍按原规则应用时段默认限制。
- 生效与休息时长均为 1～1440 分钟，最大值不得小于最小值。每策略最多 128 个时间窗口；跨午夜窗口按开始日期归属，午夜不会重置该窗口的随机段。窗口结束会截断当前随机段。
- 随机种子保存到策略 JSON。同一用户、规则与窗口在不同进程／重启后得到相同决定；缓存不跨分钟，不产生逐请求重新抽样。不同用户可有不同区间。
- 池最多引用 64 个完整普通策略；每个保持段从启用的成员中等概率选择一个，可连续两段选到同一个成员。保持区间最短／最长均为 1～1440 分钟。按池时区的本地日期确定分段，每到本地午夜重建分段，因此最后一段会被午夜截断；请求和重试期间已解析的策略不切换。
- 池基础限制与所选成员完整策略（包括成员自己的时段）合并，数值严格者优先；同来源动作仍沿用原有优先级。互不相交的两个允许名单表示全部拒绝，不会因为交集为空变成无限制。
- 不支持嵌套池；不允许把被其他池引用的普通策略改成池；删除被池引用的策略会拒绝。成员不存在、全部禁用或发现非法嵌套时请求返回不可用错误，不沿旧故障放行路径绕过管控。并发管理员修改造成的失效引用同样拒绝请求。
- 不新增数据库表，复用命名策略记录、版本、绑定和委派权限。`limits.random_pool` 仅位于基础限制，不能嵌入专项子规则或时间窗口；如需按时段执行动作，在被引用完整策略内配置时段。

池的基础限制示例（编号替换为实际普通策略编号）：

```json
{
  "random_pool": { "policy_ids": [7, 9], "hold_min": 5, "hold_max": 15 },
  "requests": { "daily": 500 }
}
```
