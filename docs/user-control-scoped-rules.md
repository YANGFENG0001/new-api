# 用户模型／渠道专项管控

## 界面入口

**系统设置 → 安全与限制 → 用户管控 → 策略 → 新建／编辑 → 模型与渠道专项管控**。

基础限制、时段限制、未命中时段的默认限制、用户覆盖均可添加专项规则。每条规则可以独立启停。沿用既有的服务端管控权限，默认仅超级管理员有权配置，管理员需要显式授权。原有批量应用、名单和订阅套餐绑定继续适用。

## 匹配、时段和计数

- 模型精确匹配**客户端原始模型名**；渠道编号匹配**实际选择的渠道**。同时填写时采用“且”，留空的一项表示全部。
- 同一条规则中列出的多个模型／渠道共享该用户的计数桶。如需每模型独立限额，请为每个模型分别添加规则。
- 桶隔离维度：用户、策略来源、规则编号、模型集合、渠道集合。仅编辑阈值或改写动作不清空原计数。改变范围或删除重建规则会使用新桶。
- 专项限额支持：拦截、每分钟／每日请求数、并发数、每日／每月请求配额、每日／每月消费、每月输入／输出词元。专项规则不支持密钥数和突发容量；密钥数继续在用户整体限制配置。
- 时段沿用现有规则：时区、多个自定义时间段、星期、指定日期、起止日期、跨午夜。只取命中的最高时段优先级，同级限制叠加，基础限制不能被放宽。
- 策略解析缓存不跨分钟复用，时段边界不再额外延迟最多 15 秒。
- 有 Redis 时共享计数，没有 Redis 时只能单进程计数。专项计数检查遇到 Redis 故障拒绝请求，不将空结果当成未使用额度。原有整体限制的故障策略不变。
- 用量基于**真实成功结算**累计，在下一次准入时检查，不是硬预留；已在途的并发请求可导致超额。限制不追溯功能启用前的历史消费。
- 正常重试不重复计入相同规则，换渠道必须重新检查新渠道命中的规则；失败请求不虚构词元或消费。同一请求经历多条规则时，各自的请求计数均保留。
- 并发槽沿用现有 10 分钟保底过期机制；它不是跨进程长任务永久租约。

## 动作执行顺序

1. 检查原始模型权限。
2. 应用没有渠道过滤的动作，重新读取模型，检查目标模型的用户策略及令牌权限。
3. 初次选择渠道，应用匹配该渠道的动作；如果动作改变模型，重新选择合法渠道，不递归触发其他渠道动作。
4. 根据最终实际渠道检查专项限额。实际重试再次检查最终命中规则。
5. 改写结果经过原有请求验证（含词元上限），随后才进入计费和转发，或返回明确标记的模拟响应。

每个阶段内按策略优先级、规则优先级从低到高应用，用户覆盖动作最后应用；同一值最后写入者生效，同级按已有稳定来源／规则顺序处理。提示词动作按顺序累计。同一来源、同一范围的重复规则引用去重；不同名单、订阅或覆盖来源仍各自独立，重复绑定会分别执行动作，应避免重复配置。限额始终分别执行，不因动作覆盖而放宽。

## 请求改写

- 模板预填 `{"temperature": 0.7}`，可以使用合并或整体替换。
- 合并使用 JSON Merge Patch 语义：对象递归合并，数组整体替换，`null` 删除字段。保持 JSON 大整数精度，最大嵌套 32 层。
- 整体替换保留原 `model`、`group`、`stream`，其余内容来自模板。必须提供接口要求的消息或输入。
- 模板禁止直接设置模型、分组、流式开关，包括大小写和 Unicode 等价拼写；模型改用专门路由选项，不能绕过权限。
- 提示词前后拼接：Chat Completions 增加 system 消息；Responses 拼接 instructions；Claude 拼接 system，并保留已有 system 内容块与缓存控制。
- 思考等级替换支持 Chat Completions 的 `reasoning_effort` 与 Responses 的 `reasoning.effort`。Claude 不支持这一通用枚举，命中时拒绝而非静默忽略。
- 单个模板／提示词／回复内容上限 64 KiB，动作处理前后请求体上限 2 MiB。改写大请求会明确拒绝，不默默跳过规则。

## 回复替换：明确标记的模拟响应

- 可关闭、模拟文本回复、模拟 JSON 回复、模拟指定错误。不会将真实上游失败变造为成功。
- 在参数校验、权限及限额检查之后，**上游调用及预扣费之前**短路。无上游调用，无消费记录，不扣费。
- 返回 `X-New-API-Simulated: true` 与 `Cache-Control: no-store`。文本协议中也带模拟标记；任意 JSON 模式不注入内容字段以保持模板原样，由响应头标记。
- 文本支持 Chat Completions、Responses、Claude 非流式及对应 SSE 事件。任意 JSON 只允许非流式请求，流式请求明确报错，不能截断真实 SSE 或破坏工具调用。
- 指定错误使用真实 400–599 状态码，默认 429，可修改错误代码和提示内容。文本／JSON 模拟回复固定 200。

## 日志与权限

- 实际模型、真实词元、真实计费和实际成功／失败不被篡改。使用日志存储实际执行模型；用户视图可显示原始请求模型，内部原模型映射在剥离管理员元数据前应用。管理员保留真实执行信息。
- 用户日志模型筛选仍按存储的实际执行模型查询，本次只改变展示投影，不修改数据库查询语义。
- 管控审计页面显示原始模型、执行模型、渠道、规则编号（含来源）、时段、动作类型、是否模拟和实际结果。异常流结束不记为成功。
- 审计不存请求正文、回复正文、模板内容、提示词、API 密钥等；只保存非敏感标识与动作类型，规则记录最多 128 项并显式标记截断。
- 运行时管控事件从所有自身审计接口剔除，包含管理员的自身视图；管理员／超级管理员管控审计接口依然必须通过既有权限检查。

## 当前支持边界

- 动作与专项用量：HTTP Chat Completions、Responses、Claude 文本 JSON。图像、音频、异步任务和任务插件未接入专项消费结算，配置专项用量命中这些接口时明确拒绝，不伪称已限制。
- 使用专项策略的账号不开放 WebSocket，包括当前时段外但该策略其他时段包含专项规则的情况，防止连接跨时段后绕过控制。其他账号行为不变。
- 渠道动作只在初次选路应用一次，避免重试累积修改消息；重试仍会检查每个新渠道的专项限额。
- 现有策略存储在文本 JSON 列，本次不新增表／字段或数据库迁移。

## 回归验证

后端用例：`service/usercontrol/schedule_test.go` 的 `TestScoped*`，以及 `controller/user_control_runtime_test.go` 的 `TestUserControl*`。

```powershell
go test ./service/usercontrol ./controller -run 'TestScoped|TestUserControl' -count=1
```

使用既有隔离数据库 fixture（仅允许回环地址）验证 SQLite 3.50.4、MySQL 8.0.46、PostgreSQL 16.15 的策略 JSON 持久化、解析、审计写入／分页、自身审计隐藏、真实消费日志及原模型展示。MySQL 设置 `TEST_SECURITY_DIALECT=mysql`、`TEST_MYSQL_DSN`；PostgreSQL 设置 `TEST_SECURITY_DIALECT=postgres`、`TEST_POSTGRES_DSN`。密码不得写入文档或仓库。

前端验证包含专项规则过滤、限额、启停／移除、时段内保存、预填 JSON 模板、模拟错误启停及管理员审计可读展示；同时回归既有编辑弹窗、用户勾选与批量菜单。

```powershell
bun run test -- src/features/user-control/__tests__ src/i18n/__tests__/user-management-errors.test.ts src/features/users/components/__tests__/batch-actions.test.tsx
bun run typecheck
bun run build
```

组件复用：规则范围使用已有 `DelimitedInput`；折叠布局使用项目 Accordion；表单使用 Field、Input、Switch、Select；JSON 编辑复用 `JsonCodeEditor`。新增 feature 组件仅组织专项业务，不重建通用弹窗、编辑器或选择控件。

验证结果：专项后端用例在上述三个数据库通过；相关前端 6 个文件共 48 项测试、类型检查、修改范围格式／静态检查与生产构建通过。本地隔离环境浏览器已验证策略新建、保存成功以及重新编辑时保留模型、渠道及限额。
